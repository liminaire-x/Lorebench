# 0009 — 퀘스트 작업대: 누가 주고 받나, 대사, 대화창

2026-09-25 · 작업대 2 설계(구현 전) · 고치는 비용: **비쌈** (퀘스트·NPC 문서에 남는다. 첫 공개 전이라 지금은 초기화로 쌈)

> 퀘스트 단계(2026-09-27, [0015](0015-quest-stages.md)): 받는 NPC(`receiver`)는 단계의 갈 NPC(`to`, 비우면 주는 NPC)로 옮겨 간다.
> 대사 `offer`·`accepted`·`declined`는 퀘스트에, `active`·`complete`(와 0013의 셋)는 단계마다 있다.

## 방향

- NPC를 클릭했을 때의 **표준 흐름**(제안 → 수락 → 진행 → 제출)은 **퀘스트 문서**가 맡는다(퀘스트 중심).
  지금 그래프 B·C·D에서 `Quest State`가 겹치던 부분이다.
- 많은 게임처럼 **퀘스트 중심과 대화 중심을 섞는다**. 퀘스트 중심으로 가다가, 선택지가 많은 대화나 퀘스트와
  상관없는 수다가 필요해지면 대화 중심 콘텐츠(각 줄에 조건·동작을 붙이는 대화 흐름, "대화" 탭 후보)를 더한다.
  참고: Quest Machine(퀘스트 중심) + Dialogue System for Unity·Yarn Spinner·ink·articy:draft(대화 중심).

## 퀘스트에 늘어날 칸 (`quests.json`, 모두 선택)

```json
{ "id": "quest_wolf", "title": "늑대 사냥",
  "giver": "npc_guard", "receiver": "npc_smith", "requires": ["quest_sword"],
  "lines": {
    "offer":    ["늑대 3마리만 잡아주게.", "요즘 가축이 자꾸 사라지거든."],
    "active":   ["아직 늑대가 남았네."],
    "complete": ["늑대를 잡았다고? 대단하군!"] },
  "goals": [ ... ], "rewards": [ ... ] }
```

- **누가 주나는 퀘스트에 적는다**(`giver`). 퀘스트를 다른 NPC로 옮길 때 한 곳만 고친다. `receiver`가 비면 `giver`.
  `giver`가 없는 퀘스트는 지금처럼 그래프(`Reveal Quest`)로만 공개된다.
- **선행 조건은 "이 퀘스트들을 모두 완료"만**(`requires`). 다른 조건(표식, 시간 등)은 이야기가 요구할 때.
- **대사는 배열**: 한 칸 = 한 페이지, 클릭하면 다음 줄. 처음부터 배열이라 나중에 형식 번호를 올리지 않는다.
  배열의 칸은 지금 글자뿐이고, 나중에 **글자 대신 묶음**을 넣을 자리로 남긴다(아래 "나중에").
- publish 검사(예정): 없는 NPC·퀘스트를 가리키면 거부, `requires`가 돌고 돌면(영원히 못 여는 퀘스트) 거부.

NPC에는 **인사말**(배열)이 생긴다. NPC 탭의 "대화" 섹션.

```json
{ "id": "npc_guard", "name": "경비대장", "greeting": ["오, 자네 왔군.", "무슨 일인가?"] }
```

## 대화창 (NPC 클릭)

서버가 **그 플레이어의 상태로** 선택지를 계산해 연다(그 플레이어에게 해당하는 것만 보낸다).

- **할 수 있는 일이 있으면 그 퀘스트로 바로 시작한다**(퀘스트 먼저). 순서는 고정 규칙: 제출 가능 → 받을 수 있음.
  - 받을 수 있음(`!`): `offer` 대사 → 퀘스트 카드(목표·보상) → **[수락] [거절]**. 수락 = 공개(`active`). 거절은 아무 일도
    없고 다음에 또 제안받는다.
  - 제출 가능(`?`): `complete` 대사 → **[건네기]** → 회수·보상·완료(지금의 `Complete Quest`와 같은 일).
  - 끝나고 다른 일이 남아 있으면 "다른 용건" 목록.
- **할 수 있는 일이 없으면**: 인사말 + 목록 + [안녕히].
- **진행 중** 퀘스트는 **받는 NPC에게서만**, 개수와 상관없이 **늘 목록에 한 줄**로 보인다(바로 시작하지 않음).
  `active` 대사가 있으면 고를 수 있고(대사 → 진행 카드 `밀 3/10`), **없으면 보이기만 하고 고를 수 없다**.
- 수락·건네기는 **서버가 상태를 다시 확인**하고 실행한다(조작된 클라이언트 방지).
- **"제안"은 저장하지 않는다.** 대화창 안의 한 단계일 뿐이라 플레이어 기록 형식(`active`·`done`)은 그대로다.

## 대사 줄 애니메이션 (2026-09-26, 조각 3)

```json
"complete": [ { "text": "고맙네!", "animation": "animation.chief.happy" }, "약속한 에메랄드일세." ]
```

- 대사 한 줄은 **글자**, 또는 **`{ "text", "animation" }`**(그 페이지가 뜰 때 NPC가 한 번 재생). 퀘스트 대사와 NPC 인사말
  모두. 애니메이션이 없는 줄은 늘 글자로 쓰므로 옛 문서 그대로. 칸 이름은 `Play NPC Animation` 노드의 `animation`과
  맞췄다. 모르는 칸(`anim` 같은 오타)은 거부.
- **대화한 사람 화면에서만** 재생한다. 대사 페이지는 그 사람의 클라이언트가 넘기므로, 페이지가 뜰 때 그 클라이언트가
  자기 화면의 NPC에게만 튼다(`NpcEntity.playLocally`). 서버를 거치지 않아 다른 플레이어에게는 안 보인다. 대화처럼
  한 사람만의 장면은 그 사람에게만 보여주는 쪽을 골랐다. `Play NPC Animation` 노드는 지금처럼 모두에게 보인다.
- "누가 보나"는 저장되지 않고 게임 코드가 정하므로 **나중에 바꾸는 비용은 쌈**. 비싼 것은 줄 형식뿐.
- 고르지 않은 것: **그래프 완료 트리거**(`On Quest Completed` → 애니메이션)를 먼저 만드는 것. 무엇이든 붙일 수 있지만
  대사와 연출이 두 곳으로 나뉜다. 대사하며 하는 몸짓은 대사 줄에, 드문 "특별한 일"(폭죽, 아이템)은 나중에 그래프 연결로.

## 나중에 (열어 둔 것)

- **그래프와의 연결**(예: `On Quest Accepted`·`On Quest Completed` 트리거)은 보류. 작업대가 넓어지며 함께 정한다.
- 진행 중이 많을 때 한 줄로 접기.
- NPC 머리 위 `!`/`?`(플레이어마다).
- **대사 한 줄의 묶음 넓히기**: 애니메이션은 위에서 넣었다. 같은 묶음에 **시선**(말 건 플레이어 / 다른 NPC),
  **말하는 사람**(여러 NPC의 대화), **선택지**(`"알려줄까?"` → 네/아니오)를 칸으로 더할 수 있다. 줄마다 연출이 많아지면
  시네마틱과 겹치니 그때 경계를 정한다.

## 고르지 않은 것

- **NPC에 퀘스트 목록**(Quest Machine의 QuestGiver): 순서를 NPC에서 정할 수 있지만, 순서는 고정 규칙으로 정했고
  퀘스트를 옮길 때 두 곳을 고쳐야 한다.
- **`locked` 대사**(선행을 안 끝냈을 때 한 줄): 선행 퀘스트는 J 화면에서 확인하면 된다.
- **우선순위 숫자**(Skyrim): 작가가 숫자를 관리해야 한다. 고정 규칙으로 대신.
- **처음부터 대화 중심**: 가장 유연하지만 표준 흐름도 매번 조건으로 써야 하고 실수(두 번 보상 등) 여지가 크다.
- **대사 한 칸 = 긴 글 하나**: 페이지를 나눌 수 없고, 줄마다 연출을 붙일 자리가 없다.
