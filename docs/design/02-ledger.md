# 02 — 장부: 변수 목록과 칸

2026-10-02~03 · 정함 · 고치는 비용: **비쌈**(목록 파일과 장부에 남는다. 첫 공개 전이라 지금은 초기화로 쌈)

[01](01-big-picture.md)의 장부를 정한다. 작가가 만드는 칸(변수)은 한 곳의 목록에 모으고, 쓰는 곳에서는 목록에서 고른다.

## 정할 것

1. 값의 종류 — **정함**
2. 주인: 누구의 값인가 — **정함**
3. 계산하는 값(가방 속 개수, 게임 날짜)도 목록에서 고르게 하나 — **정함**: 세 가지 칸
4. 목록의 모양: 어디에, 이름과 id, 설명, 처음 값 — **정함**: 테이블
5. 퀘스트가 만드는 칸(상태·단계)과의 관계 — **정함**: 3에 합쳐짐(System field)
6. 수명: 영구 / 접속 동안 / 매일 초기화 — **정함**: 영구만

## 1. 값의 종류: 켜짐/꺼짐 + 숫자 (사용자, 2026-10-02)

- 변수는 **스위치**(켜짐/꺼짐) 또는 **숫자**. 작가 화면에서 둘이 다르게 보인다("0이 꺼짐" 같은 숨은 규칙이 없게). 속에서 어떻게
  저장하는지는 내부라 쌈.
- **넓혀 가는 방향**: 글자 같은 종류는 요구하는 이야기가 올 때 더한다. 종류를 더하는 것은 옛 목록을 깨지 않고, 빼는 것이 비싸다.
- 종이 시험: 켜짐/꺼짐(인사했나, 굴을 막았나, `늑대_잠잠`), 숫자(거절 횟수: 목걸이의 다섯 번째 거절). 글자를 요구하는 이야기는 아직 없다.
- 사례: 숫자만(Typewriter, Fallen London), 스위치 + 변수(RPG 쯔꾸르), 태그 + 점수(BetonQuest), 참/거짓·숫자·글자(Dialogue System),
  Ink(정수·소수·참/거짓·글자·목록).

## 2. 주인: 플레이어마다 (사용자, 2026-10-02)

- 변수는 지금 **플레이어마다** 하나뿐이다. Dev1이 켠 `늑대_잠잠`은 Dev2의 세상을 바꾸지 않는다.
- **넓혀 가는 방향**: 모두가 함께하는 것(메이플스토리의 이벤트 퀘스트처럼 서버 전체), 파티 단위(던전에 함께 들어간 파티)는 요구하는
  이야기가 올 때 더한다. 그때 **테이블마다** 주인 종류를 고르는 칸을 두고(4), 칸이 없으면 플레이어마다로 읽는다(옛 테이블이 그대로
  읽힘).
- 종이 시험: 이야기 아홉 개의 기록은 모두 플레이어마다다. 장부(`Owner`)는 이미 플레이어/서버 둘을 담을 수 있다.
- 사례: Typewriter(사실마다 플레이어/월드/전체), BetonQuest(플레이어 태그·점수 + 전체용, 기억), MMO의 위상 변화(같은 장소가 사람마다
  다르게 보임), 메이플스토리 이벤트(서버 전체), 파티 던전.

## 3. 세 가지 칸: System · Custom · Script (사용자, 2026-10-02)

사용자가 Jira(ScriptRunner)의 필드 구분으로 넓혔다. 작가는 셋을 **한 목록에서** 고르고, 칸의 종류가 이름표로 보여 읽기 전용인지
헷갈리지 않는다(Typewriter처럼 목록에 계산하는 값을 섞을 때의 "왜 못 바꾸지?"가 없음). 질문 5도 여기서 풀린다.

| 칸 | 누가 만드나 | 읽기/쓰기 | 예 |
|---|---|---|---|
| **System** | Lorebench가 제공 | 읽기만 | 퀘스트 상태, 지금 단계, 거절 횟수 |
| **Custom** | 작가가 종류(1)를 고르고 이름을 붙임 | 읽고 씀 | `늑대_잠잠`(스위치), `마을_평판`(숫자) |
| **Script** | 작가가 수식을 씀 | 읽기만 | `털_다_모음 = 가방 속 큰 늑대 털 ≥ 3` |

- **System은 지금 이야기가 쓰는 셋으로 시작**: 퀘스트 상태, 지금 단계, 거절 횟수(대사 조건이 이미 씀). 낮/밤, 날씨, 게임 날짜, 접속
  인원, 가방 속 [아이템] 개수, 레벨, 있는 곳 같은 후보는 요구하는 이야기가 올 때 하나씩 더한다. 이름이 작가 문서에 남으므로 더하기는
  싸고 빼기는 비싸다. "가방 속 [아이템] 개수"처럼 무엇을 셀지 함께 고르는 칸은 4에서.
- **Script는 자리만.** 수식을 어떤 말로 쓰나(자체 수식, Lua, Molang …)와 서버를 멈추지 않게 하는 법은 요구하는 이야기가 올 때 따로
  다룬다.
- 사례: Jira(System·Custom·Scripted field), Notion·Obsidian 수식, 엑셀, Dialogue System(조건에 Lua 식), Ink·Yarn Spinner(대본 안의 식),
  Typewriter(목록에 읽기 전용 사실을 섞음), BetonQuest·RPG 쯔꾸르(계산은 조건의 종류로 따로).

## 4. 목록의 모양: 테이블 (사용자, 2026-10-02)

사용자가 데이터베이스로 넓혔다: **테이블 = 파일 하나, 칸(column) = 변수, 줄(row) = 주인**.

| 플레이어 | 늑대_잠잠 | 굴_막음 | 마을_평판 |
|---|---|---|---|
| Dev1 | 켜짐 | 꺼짐 | 3 |
| Dev2 | 꺼짐 | 꺼짐 | 0 |

- 테이블 파일에는 **이름, 주인 종류(지금은 플레이어뿐), 칸 목록**. 칸마다 **id**(`var_` + 무작위 8자, [0004](../decisions/0004-ids-and-record-keys.md) 규칙),
  이름, 종류(1: 스위치/숫자), 처음 값(스위치는 꺼짐, 숫자는 0이 기본), 설명.
- 테이블은 어느 폴더에나 둔다(보통 이야기 폴더마다 하나). 작가가 고르는 곳에서는 **모든 테이블의 칸이 한 목록**으로 뜬다
  ("한 곳에 모아 고르기"는 파일이 아니라 에디터의 보기가 맡는다).
- **가리키기는 칸의 id로.** 칸·테이블 이름을 바꾸거나 칸을 다른 테이블로 옮겨도 깨지지 않는다. 주인 종류가 다른 테이블로 옮기는 것은
  값의 뜻이 바뀌므로 에디터가 막거나 묻는다(그때 정함).
- 주인(2)은 **테이블마다**: 지금은 줄 = 플레이어. 나중에 줄이 하나뿐인 서버 테이블(이벤트), 줄 = 파티인 테이블(던전). 한 이야기에 둘이
  필요하면 테이블을 둘 만든다.
- 세 칸(3)과의 관계: Custom = 작가가 만든 칸, Script = 계산 칸(DB의 생성 칸, Notion 수식 속성), System = Lorebench가 미리 만든
  테이블(예: "퀘스트" 테이블의 상태·단계·거절 수).
- 에디터 Players 화면이 이 표 보기가 된다(시험할 때 한 사람의 칸만 바꿔 보기). 속의 저장은 지금의 `records`(주인, 키, 값) 모양이어도
  된다(내부라 쌈).
- 줄은 **콘텐츠가 아니라 주인**이다(언리얼 DataTable은 줄이 아이템). 화면에 쓸 이름은 06에서.
- 판단(Claude, 사용자 요청): 맨땅의 개척이 아니라 검증된 부품의 조합이다. 묶음(articy:draft의 Variable set, Dialogic 2의 폴더) + 선언
  (articy·Dialogue System의 종류·처음 값·설명) + 주인별 줄(CK3의 scope, Typewriter의 플레이어/월드/전체) + 수식 칸(Notion·Airtable). 새로운
  것은 "주인 종류를 테이블마다"뿐이고 위험이 작다. 사례와 일부러 다른 곳: articy·Dialogic은 이름 경로(`묶음.변수`)로 가리켜 이름을
  바꾸면 쓰는 곳을 고쳐야 하고, CK3는 목록이 없어 오타가 새 변수가 된다. 우리는 선언 + id.
- 고르지 않은 것: **변수마다 파일 하나**(유니티 ScriptableObject 변수): 프로그래머의 방식이라 작가에게 작은 파일 수백 개가 짐이다.
  **게임 전체에 목록 하나**(Dialogue System, RPG 쯔꾸르): 이야기 폴더를 옮기면 변수가 빠진다.
- 출처: [articy Global Variables](https://www.articy.com/help/adx/Scripting_GlobalVariables.html),
  [Dialogic 2 Variables](https://docs.dialogic.pro/variables.html),
  [CK3 Variables](https://github.com/jesec/ck3-modding-wiki/blob/master/wiki_pages/Variables.md),
  [Dialogue System Database](https://pixelcrushers.com/dialogue_system/manual/html/dialogue_database.html).

## 6. 수명: 영구만 (사용자, 2026-10-03)

- 지금 모든 테이블의 값은 **영구**다.
- **넓혀 가는 방향**: 매일 퀘스트 같은 이야기가 오면 **테이블에 수명 칸**(영구 / 접속 동안 / 정해진 시간 동안 / 정해진 때까지)을 더하고,
  칸이 없으면 영구로 읽는다. 그때 "매일"이 게임 날짜인지 현실 시간인지 꼭 고른다(0013 기다림과 같은 질문, roadmap B "현실 시간 기다림").
- 종이 시험: 이야기 아홉 개와 010의 값은 모두 영구다. 기다림은 값 대신 "맡긴 날"을 적고 게임 날짜와 비교한다(System 쪽 일).
- 사례: Typewriter(Permanent·Session·Timed·Cron·Countdown Fact), WoW 일일 퀘스트·동물의 숲(매일 초기화).
  출처: [Typewriter Basic Adapter](https://docs.typewritermc.com/adapters/BasicAdapter).

## 종이 시험 (2026-10-03)

지금까지의 이야기가 쓰는 장부 값을 새 모양으로 옮겨 본다(서버 문서 기준: 대사 조건 `questState` 5곳·`stage` 5곳, 퀘스트 `timesDeclined`
5곳·`requires` 1곳, 그래프 없음).

| 이야기 | 쓰는 값 | 새 모양 |
|---|---|---|
| 001 밀 배달 | 퀘스트 상태. 처음 모양은 그래프 `flag` "인사함"(퀘스트 작업대로 옮기며 없어짐) | System(퀘스트 상태). "인사함"이라면 Custom 스위치 |
| 002 대장장이의 칼 | 퀘스트 상태 | System |
| 003 농부의 밭 | 퀘스트 상태, 수확·번식 수, `requires`(소 키우기 ← 밭일 배우기) | System(상태). 진행 수는 퀘스트 안에서만 |
| 004 잃어버린 목걸이 | 거절 횟수, 퀘스트 상태(인사말), 전용 아이템 | System(거절 횟수·상태). 전용 아이템 표식은 장부가 아니라 아이템에 |
| 005 대장장이의 내일 | 기다림(맡긴 날), 상태 `waiting` | System(상태). 맡긴 날은 퀘스트 안에서만 |
| 006 당근 도둑 | 처치 수 | 퀘스트 안에서만 |
| 007 딸에게 가는 목걸이 | 지금 단계, 단계가 주는 전용 아이템 | System(지금 단계) |
| 008 경비대장의 걱정 | 인사말의 단계 조건 | System(지금 단계) |
| 009 조각이 다 모이면 | 다 채웠나(가방 + 진행 수) | 화면이 계산(거울). 작가가 쓰고 싶어지면 Script 칸 자리 |
| 010 늑대 무리(보류) | 장면에는 없음. 갈림 예시의 `늑대_잠잠` | Custom 스위치("늑대 무리" 테이블) |

- **깨지는 이야기는 없다.** 작가 조건이 쓰는 값은 정확히 System의 셋(퀘스트 상태·지금 단계·거절 횟수)이다.
- 진행 수·맡긴 날은 장부에 있지만 작가에게 System 칸으로 내놓지 않는다(퀘스트 안에서만). 요구하는 이야기가 오면 내놓는다.
- 전용 아이템 표식(0012)은 장부가 아니라 아이템에 붙는다. 퀘스트·물건 주제에서 다룬다.
- `requires`는 "다른 퀘스트의 상태 = 완료"라는 조건이다. 03(퀘스트)에서 조건 모양으로 다룬다.
- Custom을 실제로 쓴 이야기는 아직 없다(첫 이야기의 처음 모양뿐). 테이블은 첫 Custom 칸이 필요한 이야기(갈림, 세상의 반응)에서 처음
  쓰인다.
